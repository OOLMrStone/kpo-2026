# Домашнее задание 1. ВышКат

Консольное приложение для учёта транспорта и вещей. Используются Java 25, Gradle Wrapper, Spring IoC, JUnit 5, JaCoCo и Checkstyle.

## Запуск

Команды нужно выполнять из корня репозитория. Для запуска нужна JDK 25. При первом запуске Gradle скачает зависимости.

```bash
# Демо с готовыми командами.
./gradlew :modules:homework-1:run --args="--demo" --console=plain

# Режим с ручным вводом.
./gradlew :modules:homework-1:run --console=plain

# Тесты, проверка стиля и покрытия.
./gradlew :modules:homework-1:check --console=plain

# Сборка приложения со скриптом запуска.
./gradlew :modules:homework-1:installDist
modules/homework-1/build/install/homework-1/bin/homework-1 --demo
```

В Windows нужно использовать `gradlew.bat` и скрипт `homework-1.bat` в папке собранного приложения.

В меню есть команды:

- `1`: принять транспорт.
- `2`: добавить вещь.
- `3`: вывести отчёт.
- `4`: показать транспорт для новичков.
- `5`: показать весь инвентарь.
- `0`: выйти.

Каждое значение вводится на отдельной строке. В расходе энергии можно использовать точку или запятую. Если введено неправильное значение, программа покажет ошибку и вернётся в меню. Если ввод закончился до заполнения всех полей, объект не добавится.

Данные хранятся в памяти. После перезапуска парк снова пустой. База данных и аренда в этой работе не реализованы.

## Как устроена программа

| Тип | Для чего нужен |
| --- | --- |
| [InventoryItem](src/main/java/studying/vyshkat/model/InventoryItem.java) | Общий интерфейс для объектов с названием и инвентарным номером. |
| [EnergyConsumer](src/main/java/studying/vyshkat/model/EnergyConsumer.java) | Интерфейс для объектов с суточным расходом энергии в кВт*ч. |
| [Asset](src/main/java/studying/vyshkat/model/Asset.java) | Хранит название и номер, проверяет их при создании. |
| [Transport](src/main/java/studying/vyshkat/model/Transport.java) | Хранит общие данные транспорта: простоту от 1 до 10 и техническое состояние. |
| [ElectricTransport](src/main/java/studying/vyshkat/model/ElectricTransport.java) | Добавляет расход энергии. От него наследуются `Scooter` и `ElectricBicycle`. |
| [Bicycle](src/main/java/studying/vyshkat/model/Bicycle.java) | Обычный велосипед, который не потребляет электричество. |
| [Thing](src/main/java/studying/vyshkat/model/Thing.java) | Общий класс вещей. От него наследуются шлем `Helmet` и зарядная станция `ChargingStation`. |
| [ServiceCenter](src/main/java/studying/vyshkat/service/ServiceCenter.java) | Интерфейс техосмотра, который решает, можно ли принять транспорт. |
| [FleetService](src/main/java/studying/vyshkat/service/FleetService.java) | Учитывает транспорт и вещи, считает показатели и выбирает транспорт для новичков. |
| [ConsoleApplication](src/main/java/studying/vyshkat/console/ConsoleApplication.java) | Читает команды, создаёт объекты из введённых данных и выводит результаты. |

Инвентарный номер должен быть уникальным среди всех вещей и транспорта. Пробелы по краям удаляются, но регистр учитывается: `S-1` и `s-1` считаются разными номерами. Название и номер не могут быть пустыми. Простота должна быть от 1 до 10, расход энергии не может быть отрицательным. Для расхода используется `BigDecimal`, чтобы точно складывать введённые десятичные числа.

При добавлении транспорта пользователь указывает, исправен ли он. [TechnicalServiceCenter](src/main/java/studying/vyshkat/service/TechnicalServiceCenter.java) проверяет это значение и принимает только исправный транспорт. Само поле `operational` хранит состояние, а решение о приёмке получается через вызов сервиса.

В `FleetService.admit` сначала проверяется номер, затем выполняется техосмотр. Только после одобрения транспорт добавляется в реестр. Если техосмотр отказал или выбросил исключение, реестр не меняется, а номер остаётся свободным. Вещи добавляются отдельно без техосмотра, потому что по условию он нужен для прокатного транспорта.

В список для новичков попадает принятый транспорт с простотой от 6. Шлемы и станции в этот список не входят. В отчёте выводятся число единиц транспорта, число вещей, общее количество объектов и суточный расход энергии. При расчёте учитываются все объекты с интерфейсом `EnergyConsumer`, в том числе зарядные станции. У станции указывается её собственный расход, чтобы не считать энергию транспорта дважды. Отклонённый транспорт в отчётах не учитывается.

Сервис возвращает копии списков, которые нельзя изменить. Если после получения списка добавить объект в парк, старый список останется прежним. Поля объектов тоже нельзя изменить после создания, поэтому зарегистрированный номер не поменяется. Программа рассчитана на работу в одном потоке.

## SOLID и обязательные вопросы

| Принцип | Как применён |
| --- | --- |
| SRP, единственная ответственность. | Модель проверяет свои данные, `ServiceCenter` проводит техосмотр, `FleetService` ведёт учёт, `ConsoleApplication` отвечает за ввод и вывод. |
| OCP, открытость расширению. | Новый наследник `Transport` работает с приёмкой и отчётами без изменения `FleetService`. Для учёта расхода энергии достаточно реализовать `EnergyConsumer`. |
| LSP, подстановка наследников. | В сервис можно передать любой вид `Transport`. Все виды сохраняют общие правила для номера и простоты. Велосипеду не нужны методы батареи. |
| ISP, разделение интерфейсов. | Учёт и расход энергии разделены на два интерфейса. Шлему и обычному велосипеду не нужно реализовывать расход и возвращать ноль. |
| DIP, инверсия зависимостей. | `FleetService` получает `ServiceCenter` через конструктор. Конкретный `TechnicalServiceCenter` внутри него не создаётся. |

**Какой принцип применён наиболее явно?** DIP. В [ApplicationConfiguration](src/main/java/studying/vyshkat/ApplicationConfiguration.java) описано создание двух компонентов. Spring создаёт сервис техосмотра и передаёт его в `FleetService`. При замене техосмотра основной сервис менять не нужно. Классы модели от Spring не зависят. `getBean` вызывается только в `Main` при запуске, внутри `FleetService` обращения к контейнеру нет.

**Какой принцип ограничен и почему?** OCP в консольном меню. При добавлении нового транспорта нужно дописать вариант в `ConsoleApplication.addTransport`, чтобы пользователь мог его выбрать. При этом приёмка, учёт энергии и выбор транспорта для новичков продолжат работать. Для трёх видов транспорта я оставил обычный `switch`. Отдельная система фабрик здесь только усложнила бы код. По той же причине хранение в памяти и простые подсчёты находятся вместе в `FleetService`.

**Что будет при расширении?** Новый вид транспорта может наследоваться от `Transport`, а электрический от `ElectricTransport`. Пример добавления нового вида есть в тесте `extensionUsesExistingContracts`. Для сотрудника нужен отдельный класс и отдельный учёт, так как сотрудники по условию не ставятся на баланс. Запчасть с собственным инвентарным номером может наследоваться от `Thing`. Если нужно хранить количество одинаковых запчастей, потребуется отдельный складской учёт. Эти изменения не должны затрагивать приёмку транспорта.

**Какие тесты проверяют техосмотр и правило для новичков?** В [FleetServiceTest](src/test/java/studying/vyshkat/FleetServiceTest.java) тест `rejectedTransportDoesNotEnterAnyReport` передаёт через конструктор заглушку `transport -> false`. Она всегда отказывает, и тест проверяет, что транспорт не попал в парк и отчёты. Тест `inspectionRunsBeforeRegistration` проверяет, что техосмотр вызывается один раз и до записи в реестр. `beginnerBoundary` проверяет простоту 1, 5, 6 и 10. В [ContainerTest](src/test/java/studying/vyshkat/ContainerTest.java) тест `containerInjectsFakeInspection` заменяет техосмотр через Spring: тестовый компонент `ServiceCenter` получает приоритет, и контейнер передаёт его в `FleetService`. Отдельный тест проверяет обычную конфигурацию.

Роль ИИ и мои доработки описаны в разделе "Использование ИИ" ниже.

## Демонстрация и проверка

Режим `--demo` подставляет готовые команды вместо ручного ввода. Он использует то же меню и тот же Spring-контейнер, что и обычный запуск. Тесты также проверяют допустимые и недопустимые значения, точность суммы энергии, неизменяемость списков, ошибку техосмотра, новый вид транспорта, конец ввода и возврат в меню после ошибок. Для самих тестов не нужны сеть и внешние сервисы.

После команды `check` отчёты находятся в папке модуля:

Результат проверки: 57 тестов, покрытие строк 99.34%, покрытие ветвей 94.83%. Полная команда `./gradlew check` также проверяет практики 1 и 2. Собранное приложение проверено в деморежиме и с вводом команд.

## Использование ИИ

Сначала мы вместе с ИИ разобрали условие и придумали архитектуру приложения. Решили отдельно сделать классы транспорта и вещей, сервис для учёта и консольное меню. После этого с помощью ИИ реализовали эту структуру, а затем я попросил разбить часть кода на небольшие методы, чтобы его было проще читать и не повторять одинаковые действия.

При обсуждении модели мы выделили общие название и номер в `Asset`, а транспорт и вещи разделили на `Transport` и `Thing`. Расход электричества вынесли в `EnergyConsumer`, потому что он нужен только части объектов. Также решили отделить техосмотр от учёта, чтобы можно было заменить его правила и проверить отказ в тестах.

После реализации я предложил доработать декомпозицию. Для этого попросил ИИ вынести повторяющиеся проверки и чтение данных в отдельные методы:

- Я попросил вынести проверку уникальности инвентарного номера в `requireAvailableNumber` в `FleetService`. Она нужна и для транспорта, и для вещей. Теперь оба метода добавления вызывают одну проверку. При приёмке транспорта номер проверяется до техосмотра.
- Чтение расхода энергии я попросил вынести в `readEnergy`. Метод читает число и переводит его в `BigDecimal`. Также заменяет запятую на точку, поэтому можно ввести и `1.5`, и `1,5`. Он используется при добавлении самоката, электровелосипеда и зарядной станции.
- Для технического состояния выделили `readCondition`. Он принимает `1`, если транспорт исправен, и `0`, если нет. При другом ответе выдаётся ошибка. В методе добавления транспорта теперь не нужно отдельно разбирать этот ответ.
- Общий ввод строки находится в `read`. Метод показывает, что нужно ввести, читает строку и убирает пробелы по краям. Через него читаются команды меню, название, номер и остальные поля.
- Добавление разделили на `addTransport` и `addThing`. У транспорта нужно прочитать простоту и состояние, после чего провести техосмотр. У вещей этих шагов нет. В `run` остались цикл меню, вызовы нужных методов и обработка ошибок.
- Отчёт выводится в `report`, а списки объектов в `printItems`. Один и тот же `printItems` показывает весь инвентарь и транспорт для новичков. Сообщение о пустом списке тоже задаётся один раз.
- Проверку названия и номера собрали в `Asset.requiredText`. Он отклоняет `null`, пустую строку и строку из пробелов. Затем убирает пробелы по краям. Проверка используется для обоих полей и всех наследников.
- Для проверки расхода выделили `EnergyUsage.validate`. Он не разрешает `null` и отрицательные значения, но допускает ноль. Проверка находится в модели, поэтому работает и при создании объекта напрямую из кода.
- Подсчёт транспорта, расхода и выбор транспорта для новичков выполняют `transportCount`, `totalDailyEnergyKwh` и `beginnerTransport`. Консоль вызывает их и выводит результат. Сами расчёты остаются в сервисе.

Например, после такого разделения в `admit` видны три основных шага: проверить номер, провести техосмотр и добавить транспорт. Подробности проверки номера находятся отдельно и не повторяются при добавлении вещи.

ИИ помог с реализацией, тестами, документацией и запуском проверок. Моя часть работы состояла в обсуждении архитектуры и выборе того, какие операции вынести в отдельные методы. Эти изменения тоже вносились с помощью ИИ.
